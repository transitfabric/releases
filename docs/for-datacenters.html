Fabric for data centres and hosting providers

Status of this page: Transit Fabric is live on Bittensor testnet, with mainnet planned for 1 January 2027. Testnet nodes earn points under the testnet rules; that page is the only source for what testnet work may earn. Routing between nodes, capacity tests and scoring run on testnet today. Everything marked planned on this page is not built yet and carries a target date. Target dates are targets, not commitments, and can move.

This page is for a data centre or hosting provider that wants to know what running Fabric nodes involves, and what it does not. It is a factual summary, not a sales pitch.

What you have

  • Servers or racks with committed transit and good upstream connectivity.
  • Bandwidth that sits idle outside your busy hours.
  • Possibly your own ASN, exchange ports and cross-connects.

What Fabric does with it

Fabric is a decentralized network fabric run as a Bittensor subnet. Nodes carry overlay traffic for each other. Customers of the fabric are companies that link sites and clusters, and VPN providers that move traffic between their servers. Capacity in data centres is what that traffic crosses, so the network measures it and prefers measured, real capacity.

A data centre can take part as a node operator today on testnet, and as a registered gateway operator once gateways are built (planned: our own gateway runs on testnet first, ahead of the 1 January 2027 launch target, and outside operators follow after launch).

What you would run

Every node speaks real eBGP over WireGuard and has an address derived from its own key. A node is either public or behind NAT, and has some capacity. It is not classed as "home" or "datacentre". Route solvers are a separate role, not a node, and any Linux machine with a public IPv4 address can run one.

Nodes in separate sites on separate networks count separately. For testnet reward points, two nodes in one /24 count once, so running several nodes in one block adds nothing. Use a dedicated machine for a kernel node.

What your network must allow

These are requirements only, and they come from the operator guide. Check them before you register.

  • UDP. WireGuard runs over UDP: one port per peer on a kernel node, and port 51820 on a public no-root node. Steady UDP is normal, but some networks filter or rate-limit what looks like a sustained UDP flood. If sessions drop under load, check your own filters first.
  • TCP 8621 inbound on a public node, for the capacity-test sink, and UDP 8620 inbound from any address, for other nodes' direct probes.
  • Outbound: UDP to the validators' probe agents and TCP to their object stores. Behind NAT, also TCP to the probe agents' hosts for capacity tests. Outbound traffic is normally allowed; if you filter it, allow all three.
  • IPv4 and IPv6. A kernel node needs a public IPv4 address. Inside the overlay every node has an IPv6 address in fc00::/8, so IPv6 forwarding is on for the host.
  • Traffic allowance. Capacity tests and carried traffic use bandwidth. On a metered or capped plan, work out what a month costs before you declare capacity. On a 95th-percentile plan, capacity tests can use about half of the monthly burst allowance (see the FAQ).
  • Your own address block. For testnet reward points, two nodes in the same /24 count once, whoever runs them. On-chain scoring is set in the scoring spec.
  • Upstream BGP kept apart. A node that also peers with an upstream provider holds that session in its own routing instance. Overlay routes are never announced to the provider, and provider routes never enter the overlay. A single-network-interface host can't do this yet.

How it is measured and paid

Validators probe every node and run capacity tests. They score what a node measurably carries: it needs to be up, to pass a capacity test and to declare no more than it can carry. Validators compute scores from the same committed inputs, so any honest validator gets the same result, and you can recompute it yourself with a shadow validator (see the shadow validator guide).

Pay follows measured contribution. It does not follow what a node claims, how big its owner is or who it knows. A node that performs poorly earns little, and so does one that overstates its capacity. Declaring less than you have is free and can be changed at any time; raising a declaration waits for the next epoch.

Capacity above the bar, several UIDs on one machine and several nodes in one /24 do not earn more.

What it is not

  • Not an exit. Transit nodes never send traffic to the public internet. Traffic on a node's links stays inside the overlay, and a forward filter drops anything else. Only registered exit partners and registered gateways ever do, under their own rules.
  • Not a way to choose your own traffic. Transit is rewarded only on paths the network assigns, or on test traffic from a shared schedule that everyone can check.
  • Not a provider list. This page names no hosting providers, ISPs or VPN companies. It lists what a network must allow, and what works depends on your plan and region.
  • Not a promise of income. Nothing here is an earnings, price or return claim, and no price is quoted on this page.
  • No abuse complaints from transit. Because transit nodes never egress, traffic that crosses your node is not traffic that leaves from your IP space to the public internet. That is the main reason this role is open to data centres.

Where it stands

  • Live on testnet: nodes, peering over BGP and WireGuard, capacity tests, scoring and route solving on Bittensor testnet.
  • Mainnet: planned for 1 January 2027.
  • Planned (our own gateway first, on testnet, before launch; outside operators after launch): registered gateways run by data centre operators. A gateway operator needs to prove control of its own ASN with RPKI, have a working abuse contact in a public peering database and sign a binding of the gateway key to its identity. Gateways egress only paid, authorised traffic to destinations a customer has named. This is being built and is not live.

  2. Follow the quick start: wallet, download, node, peer, check. Testnet only: use your own nodes and test TAO, never a mainnet wallet.
  3. Read the FAQ for who the customers are, how capacity is bought and what carrying traffic costs an operator.
