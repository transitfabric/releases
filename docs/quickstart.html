Quick start

This release joins Bittensor testnet, subnet 611. Testnet only: never use a mainnet wallet. The full guide ships with each release, as testers.md.

Already running a node from an earlier release? Don’t start over: update it to tester.5.1 or later before Sat 2026-11-28 14:51 UTC (nodes and solvers use tester.5.1; validators and shadow validators use tester.5.3.1). The upgrade steps work from any earlier release. The node keeps its key, binding and credit.

1. Wallet and UID

Use a new wallet, never your mainnet coldkey. Get test TAO from the Bittensor community Discord. We don't hand it out.

btcli wallet create --wallet-name tf-test --hotkey default
btcli subnets register --network test --netuid 611 --wallet-name tf-test --hotkey default
btcli wallet overview --wallet-name tf-test --netuid 611 --network test
btcli wallet transfer --wallet-name tf-test --network test --dest <hotkey SS58> --amount 0.1

The last command sends a little test TAO to the hotkey for fees.

2. Check the download

Download from the Releases page. Compare sha256sum SHA256SUMS with the hash in our announcement. Then run sha256sum -c --ignore-missing SHA256SUMS. You need validator-set.json and network.json for every path.

You don’t rebuild validator-set.json by hand. A node that runs System One (install.sh --fabric-sense ... --network-json network.json, the container, or fabric-sense entrypoint for a process) builds a current set from the chain when it starts. It takes the set only if it passes the unattended check against the release’s copy: more than 2/3 of the stake shared, and no validator’s share up by more than 10 points. If the build fails, the node starts on the release’s copy and bwos doctor says why (validator_set_pinned), and System One keeps retrying. On a kernel node, a set that goes stale later is left as a candidate, and bwos doctor names the command that adopts it. Only a solver builds one by hand. --out refuses a file that exists, so write validator-set.new.json and then mv it over validator-set.json.

UDP 8620 is the direct-echo responder. Other nodes send signed direct probes for Mechanism 1 from any address, so it can’t be limited to known addresses (path A rate-limits it itself). On path B, a public node runs the sink with it, and reads the node’s own attested directory from its state. The sink must see each probe’s real source address. In Docker, use --network host (and leave out the -p flags), or publish with Docker’s userland proxy off ("userland-proxy": false in /etc/docker/daemon.json), never through docker-proxy. For example:

docker run --cap-drop=ALL --user 65534:65534 --read-only -v <keys>:/keys:ro -v <state>:/state:ro \
  -p 8621:8621/tcp -p 8620:8620/udp --entrypoint /bwos-probe bwos-node:<v> \
  cap-sink -node-key /keys/node.key -listen 0.0.0.0:8621 -echo -persist \
  -direct-echo 0.0.0.0:8620 -peer-dir /state/signed-inputs.json

4. Keys and consent, on each node

Path B shown. Path A uses /etc/bwos and root.

Already have keys? Skip this step. To move a Docker node to a new release, see Upgrade a node.

./bwos-node keygen -key keys/node.key
./bwos-node wg-bind -key keys/node.key -wg-key keys/wg.key -out keys/wg-binding.json -not-before 1 -not-after 100000000 >/dev/null
./bwos-node link-url -key keys/node.key -base http://localhost:8000/ -hotkey <hotkey SS58> -netuid 611 -not-after 100000000 -out keys/consent.json

5. Link to your hotkey

You can link up to 7 nodes, on any OS. Unpack the link page, serve it on your own machine, and open it:

tar -xzf bwos-link-page-<v>.tar.gz && cd bwos-link-page
python3 -m http.server 8000 --bind localhost

Open http://localhost:8000/. Paste the nodes' link URLs and choose test. Connect the wallet that holds your hotkey. Keep "inline" ticked, then sign and commit. Each node then hands its consent to every validator over its probe sessions. You send us nothing. On macOS or Linux you can use bwos bind instead (the macOS build is bwos-macos-universal-<v>.tar.gz).

5b. Declare capacity

A node is not paid on Mechanism 0 without a signed capacity declaration and a fresh manifest, renewed every window. Do this after step 5, once the inline binding is on chain. It runs on the computer that holds your hotkey file, and stays on. Give each node as <node public key hex>=<Mb/s>, using the key from bwos-node id -json -key keys/node.key, and declare what the node really carries. Validators test it.

./bwos declare keepalive --network test --netuid 611 --hotkey ~/.bittensor/wallets/tf-test/hotkeys/default \
  --node <node public key hex>=500 --state-dir declare-state --deliver ./keys --once

That first pass signs the declaration and writes the files in keys/. Then start the node with these flags, once:

--forward-object commitment-manifest=keys/commitment-manifest.json \
--forward-object capacity-declaration=keys/capacity-declaration.json \
--forward-object commitment-manifest=keys/commitment-manifest-1.json \
--forward-object commitment-manifest=keys/commitment-manifest-2.json

On path A, pass the same --forward-object flags to install.sh, and deliver with --deliver root@<node host>:/var/lib/bwos/probe. Then run the same bwos declare keepalive command without --once. Each window it re-signs if needed, re-commits the manifest and delivers the files. If your computer is off for more than a window, the declaration lapses and the node earns nothing until it is back. The release guide, section 4e, has the details.

6. Get a peer

A node is paid for capacity only with a BGP session to a node of another UID. Until scoring version 2 starts, at block 8,544,960 (about Sat 2026-11-28 16:03 UTC), peering is by hand. Make your peer card (the release guide, section 5) and post it in a Peering request Issue. Take transit_peers[0] from network.json as your peer. Our node adds yours by itself once validators list your node. It takes one node per UID, first come. Or swap cards with another tester. At least one side must be public.

From scoring version 2, peering is automatic for nodes that opt in. A kernel node adds a "peering" section to node.json. A public no-root or container node passes --public, with --validators and --node-key. Validators then draw your node’s peers each window (the release guide, section 5).

7. Run, then check

  • bwos doctor --json on the node: every check ok. If it names a fix, do that first.
  • In NodeStats: probe_peers[].session: true and forwarded_sent above 0.
  • In the log: SessionUp with your peer, and TableApplied.
  • On chain: bwos-validator chain-status --network test --netuid 611 shows your inline_nodes and the validators' weights for your UID.
  • btcli subnets metagraph --netuid 611 --network test shows incentive.

First weights come one to two windows after you are up, peered and linked. A window is about 72 minutes. Expect about 220 Mb/s per flow on cloud VMs.

Problems

Open an Issue. Use the Bug report form: give the version (bwos-node --version), your path, the output of bwos doctor --json and the issue-body.md that bwos report writes. It removes keys and addresses. For security findings, or ways to earn more than you carry, use Report a vulnerability. Never send a private key, seed phrase or wallet file.
