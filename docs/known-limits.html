Known limits: v0.1.0-tester.5

The release that schedules scoring version 2 (automatic peering and Mechanism 1 grading on drawn pairs) at block 8,544,960, about Sat 2026-11-28 16:03 UTC. The fifth build for outside testers, on Bittensor testnet, subnet 611. Please read these before you report a bug. They are known, and most have a task to fix them.

What is in it

  • Nodes, mechanism 0. bwos-node for Linux x86_64 and aarch64. One static binary serves both kinds of node: a kernel node (Ubuntu 24.04, kernel WireGuard and FRR 10, set up by install.sh) and a no-root node (bwos-node run --mode userspace, a plain process or the container image). Both open probe sessions to every validator, answer probes, hand over the node's consent, and take capacity tests.
  • Linking, without a server. Bind up to 7 nodes to your hotkey inline, with the link page or with bwos bind ... commit --inline on Linux.
  • Solvers, mechanism 1. bwos-solver daemon fetches each window's snapshot, runs your solver (--solver-cmd, any language), signs and commits the table, and serves it for validators to pull. minimal_solver is a starting point.
  • Router. The Linksys WRT1900AC v1 image (stock OpenWrt 24.10.4 plus the Transit Fabric packages), and the packages on their own.
  • System One. fabric-sense, the node's watchdog: it builds a current validator set when the node first starts, checked against the release's copy, and keeps rebuilding a stale one (a kernel node adopts a later one only by your command) and sends signed crash reports, counts only. bwos doctor --json checks a node; bwos report builds a redacted bug report.
  • Shadow mode. bwos-validator shadow recomputes every window's weights from public, committed data and compares them with what each validator revealed on chain. It holds no usable key and never writes to the chain. A MISMATCH is bounty-eligible: guide.
  • For AI agents. A Claude Code skill, llms.txt and AGENTS.md.
  • Checking. bwos-validator chain-status --network test --netuid 611, a read-only JSON view of each UID's commitment, axon and weights.

Known limitations

  • Moving to the rebuilt fleet needs this release. The fleet was rebuilt on 2026-11-20 with new addresses and validator keys. A node on tester.4.3 or earlier can’t reach it, and from 2026-11-21 19:40 UTC its System One builds sets the new validators don’t sign. bwos doctor reports validator_set_retired on a node that still trusts the old validators. The steps are on Move to tester.4.4.
  • Automatic peering starts with scoring version 2. From block 8,544,960 (about 2026-11-28 16:03 UTC); the first pairs are drawn into window 23,737. A node takes part only if it opts in: "peering" in a kernel node’s node.json, or --public (with --validators and --node-key) on a public no-root or container node. Until then, peer with our public node (transit_peers) or swap cards with another tester.
  • The data-plane gate is off. It runs in shadow and changes no weight in this release.
  • Mechanism 1 pays outside solvers almost nothing for two windows. Windows 23,736 and 23,737 have no drawn-pair measurements to grade against, so that weight goes to our first-party UID; solvers’ share comes back as the draw adds pairs.
  • Container nodes: recreate, don't just restart. A container node's command line carries --probe-peer and the --directory-url, --table-url and --snapshot-url lists from the network.json it was installed from, so an upgrade that changes them means recreating the container. sudo bash migrate-4.4.sh container <name> in this release does it with your options and volumes kept (Move to tester.4.4). A later release takes the lists from network.json itself (PB-69).
  • System One is rules only, and does two jobs. It rebuilds the anchor and reports faults. It doesn't peer, renew capacity declarations or fix NAT yet, and there is no model in it.
  • The release's anchor must be under 30 days old, and the validator set must not have changed much since. A node checks the set it builds at first start against the copy in the release. An older release, or one cut before a validator joined, left or rotated its key, may not bootstrap: the node starts on the release's copy and bwos doctor shows validator_set_pinned. We cut a release after any validator-set change.
  • The owner names the validators. From testnet block 8,538,840 (about 2026-11-27 19:40 UTC; tester.4.4 moved it from 8,495,640) the validator set is built from the chain alone: the hotkeys the subnet owner lists in a coldkey-signed list on chain. Whoever holds the subnet's owner hotkey, now or later, decides that list. Outside validators are admitted by a later rule, published before any outside validator joins. The 7-day lead between the owner-hotkey rotation and activation is waived on testnet: the rotation is verified on both read sources, and any owner-coldkey carrier can recommit the signed list.
  • Either read source's outage pauses every validator. A chain read stands only with two agreeing answers, so an outage, a rate limit or a lag of more than 4 blocks on either source holds the reads it can't serve, then abstains. A read below block 8,453,375 is taken from the public archive alone until block 8,513,640 (about 2026-11-24).
  • Mechanism 0 shadow results are often MISMATCH_INPUTS_INCOMPLETE. Receipts aren't a committed input yet, so a shadow can't prove a Mechanism 0 difference in a window with live nodes. Mechanism 1 differences are findings.
  • Validators are ours. The Transit Fabric team runs every validator on 611. Some measurements come from probe sessions that aren't yet matched to where their results are collected, so one operator could answer different validators from different machines (threat T300). We accept that on testnet only while every validator is ours. It must close before any outside validator takes part.
  • Capacity is tested one network at a time. Tests are drawn per network (/24 for IPv4). One machine behind several networks' addresses is tested at different times, and each test sees its whole rate. From testnet block 8,536,320 (scoring version 1, about 2026-11-27 11:15 UTC), validators also co-test all of a UID's nodes behind NAT at once, about every other window. Please don't exploit it; report what you find.
  • Behind NAT, capacity counts at most 100 Mb/s. A node behind NAT is capacity-tested by dialing out to the validator. That method is interim and credits at most 100 Mb/s, whatever the node carries. A public node with TCP 8621 open is tested at its full rate.
  • About 220 Mb/s per flow. On cloud VMs, one flow over the overlay (UDP, userspace WireGuard) carries about 220 Mb/s, so a single-flow test tops out there.
  • No customer traffic. Nodes carry only other nodes' overlay traffic and validators' test traffic. There is no VPN exit, and nothing goes out to the public internet.
  • Peering is self-service, with limits. A node is paid for capacity only with a BGP session to a node of another UID, and Transit Fabric doesn't assign peers yet. Our public node in network.json's transit_peers adds your node by itself once you post your peer card in a "Peering request" Issue and validators list your node (testers.md section 5). It takes one node per UID and sixteen testers' nodes in all, first come. You can also swap cards with another tester. Two nodes both behind NAT can't peer, because there's no hole punching yet.
  • Router nodes aren't measured yet. The router package has no probe sessions, so a router node can peer and carry traffic, but validators can't measure or pay it, and it has no System One.
  • Mac: the bwos CLI only, unsigned. bwos-macos-universal-v0.1.0-tester.5.tar.gz (Intel and Apple silicon) links nodes and declares capacity from a Mac. If Gatekeeper blocks it, run xattr -d com.apple.quarantine bwos. Nodes run on Linux. There are no Windows binaries; Windows users link nodes with the link page. btcli works everywhere.
  • The probe agents are listed by hand. network.json lists each validator's probe agent, and nodes don't yet read them from the signed validator set. If we add or move a validator, we'll publish a new network.json.
  • A solver starts from a current set. A node builds its own at first start, but a solver doesn't yet: if the release's validator-set.json is more than about a day old, build a current one first (testers.md section 9). The node's stats show the set it holds (set_block, set_not_after).
  • Releases aren't signed yet. Check SHA256SUMS against the hash we announce by a second route.
  • More than 7 nodes on one hotkey need manifest mode. Its manifest must be re-committed at least every other window (about 2.4 hours; OQ-210), and a node can forward its files only up to about 13 nodes. With more than 16 nodes, a validator reveals at most 16 consents per UID (OQ-263).
  • The reference solver earns nothing, and neither will minimal_solver: a table must beat the reference by 2% to be paid.
  • Prototype data plane. A packet's source is checked only as far as the link it came on. Link reports are what each node says of itself, unsigned (run-a-node.md, "What's missing").
