Known limits: v0.1.0-tester.3

The third build for outside testers, on Bittensor testnet, subnet 611. Please read these before you report a bug. They are known, and most have a task to fix them.

What is in it

  • Nodes, mechanism 0. bwos-node for Linux x86_64 and aarch64. One static binary serves both kinds of node: a kernel node (Ubuntu 24.04, kernel WireGuard and FRR 10, set up by install.sh) and a no-root node (bwos-node run --mode userspace, a plain process or the container image). Both open probe sessions to every validator, answer probes, hand over the node's consent, and take capacity tests.
  • Linking, without a server. Bind up to 7 nodes to your hotkey inline, with the link page or with bwos bind ... commit --inline on Linux.
  • Solvers, mechanism 1. bwos-solver daemon fetches each window's snapshot, runs your solver (--solver-cmd, any language), signs and commits the table, and serves it for validators to pull. minimal_solver is a starting point.
  • Router. The Linksys WRT1900AC v1 image (stock OpenWrt 24.10.4 plus the Transit Fabric packages), and the packages on their own.
  • System One. fabric-sense, the node's watchdog: it rebuilds a stale validator set (a kernel node adopts it only by your command) and sends signed crash reports, counts only. bwos doctor --json checks a node; bwos report builds a redacted bug report.
  • For AI agents. A Claude Code skill, llms.txt and AGENTS.md.
  • Checking. bwos-validator chain-status --network test --netuid 611, a read-only JSON view of each UID's commitment, axon and weights.

Known limitations

  • System One is rules only, and does two jobs. It rebuilds the anchor and reports faults. It doesn't peer, renew capacity declarations or fix NAT yet, and there is no model in it.
  • An old anchor at install time. If the anchor is already old when you install, the node waits for its set timer, up to about a day, before System One notices. Rebuild the anchor by hand first (quick start, step 2; OQ-295).
  • Validators are ours. The Transit Fabric team runs every validator on 611. Some measurements come from probe sessions that aren't yet matched to where their results are collected, so one operator could answer different validators from different machines (threat T300). We accept that on testnet only while every validator is ours. It must close before any outside validator takes part.
  • Capacity is tested one network at a time. Tests are drawn per network (/24 for IPv4). One machine behind several networks' addresses is tested at different times, and each test sees its whole rate. Random spot co-tests across a UID's networks come later (OQ-286). Please don't exploit it; report what you find.
  • Behind NAT, capacity counts at most 100 Mb/s. A node behind NAT is capacity-tested by dialing out to the validator. That method is interim and credits at most 100 Mb/s, whatever the node carries. A public node with TCP 8621 open is tested at its full rate.
  • About 220 Mb/s per flow. On cloud VMs, one flow over the overlay (UDP, userspace WireGuard) carries about 220 Mb/s, so a single-flow test tops out there.
  • No customer traffic. Nodes carry only other nodes' overlay traffic and validators' test traffic. There is no VPN exit, and nothing goes out to the public internet.
  • Peering is self-service, with limits. A node is paid for capacity only with a BGP session to a node of another UID, and Transit Fabric doesn't assign peers yet. Our public node in network.json's transit_peers adds your node by itself once you post your peer card in a "Peering request" Issue and validators list your node (testers.md section 5). It takes one node per UID and four testers' nodes in all, first come. You can also swap cards with another tester. Two nodes both behind NAT can't peer, because there's no hole punching yet.
  • Router nodes aren't measured yet. The router package has no probe sessions, so a router node can peer and carry traffic, but validators can't measure or pay it, and it has no System One.
  • Mac: the bwos CLI only, unsigned. bwos-macos-universal-v0.1.0-tester.3.tar.gz (Intel and Apple silicon) links nodes and declares capacity from a Mac. If Gatekeeper blocks it, run xattr -d com.apple.quarantine bwos. Nodes run on Linux. There are no Windows binaries; Windows users link nodes with the link page. btcli works everywhere.
  • The probe agents are listed by hand. network.json lists each validator's probe agent, and nodes don't yet read them from the signed validator set. If we add or move a validator, we'll publish a new network.json.
  • Start within about 29 hours of the anchor, or build a current one. validator-set.json is good for about 29 hours from its block. A node or solver started in that time walks forward through the validators' newer sets and keeps following them. The node's stats show the set it holds (set_block, set_not_after).
  • Releases aren't signed yet. Check SHA256SUMS against the hash we announce by a second route.
  • More than 7 nodes on one hotkey need manifest mode. Its manifest must be re-committed at least every other window (about 2.4 hours; OQ-210), and a node can forward its files only up to about 13 nodes. With more than 16 nodes, a validator reveals at most 16 consents per UID (OQ-263).
  • The reference solver earns nothing, and neither will minimal_solver: a table must beat the reference by 2% to be paid.
  • Prototype data plane. A packet's source is checked only as far as the link it came on. Link reports are what each node says of itself, unsigned (run-a-node.md, "What's missing").
