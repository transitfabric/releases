Upgrade your node to tester.5.4

This page upgrades a node you already run to v0.1.0-tester.5.4, from any earlier tester release, and moves it onto the rebuilt testnet fleet if it is not there yet. Your node key, WireGuard key, binding, consent and registration stay as they are. The same steps are in the release notes of tester.4.4, tester.5, tester.5.1 and tester.5.4. New to Transit Fabric? Start with the Quick start.

Why tester.5.4, and by when

  • Every component uses tester.5.4. Nodes, solvers and the bwos CLI update before Sat 2026-11-28 14:51 UTC (block 8,544,600); validators and shadow validators update after the restart freeze ends (Fri 2026-11-27 20:51 UTC).
  • Scoring version 2 and automatic peering start at block 8,544,960 (window 23,736, about Sat 2026-11-28 16:03 UTC). From block 8,544,600 (about 14:51 UTC the same day), validators name the peer directory they attest in their chain commitments. A node on tester.4.4 or earlier can’t follow version 2, so upgrade before Sat 2026-11-28 14:51 UTC.
  • tester.5.4 fixes dual-stack --listen [::] for IPv4 peers, V2 direct-echo flood protection, install.sh stale-apply and static-peer healing, solver prior-window hydration on restart, and pre-V2 validator, probe-agent, multi-source RPC, bwos report, offline-default bwos-mcp and link-page hardening (V0, V1 and V2 weights are byte-identical to tester.5.3.1). It includes tester.5.1’s kept-alive store polling.
  • To be drawn peers automatically, opt in. A kernel node adds a "peering" section to node.json ({"port": <first UDP port>, "max_peers": <1..24>, "public": <true or false>}) and is installed with --validators and a "probe" section. A public no-root or container node runs with --validators and --node-key, and adds --public if it takes dial-ins. Without --public, its record says it is behind NAT. A node that doesn’t opt in keeps the peers you gave it. The release guide (testers.md), section 5, has the details.

Background: the 2026-11-20 fleet rebuild

On Fri 2026-11-20 at about 22:30 UTC an automated cost guard on our side deleted the whole testnet fleet: the four validators, the reference solver and our reference nodes. We have rebuilt it on new servers with new addresses, new validator attestation keys and new probe-agent keys. The validators' hotkeys, their stake and the subnet are unchanged.

Your node can't reach the old addresses, and it still trusts the old attestation keys, which no longer sign anything. So it needs this release's validator-set.json (the new validators) and network.json (their new addresses). The new fleet's addresses are reserved, so a later rebuild keeps them.

Your credit is safe

We checked each record; we didn't take it for granted.

  • Registrations and bounty claims are GitHub Issues on transitfabric/releases and were never on the fleet. All of them are still there, and nobody needs to register again.
  • Bindings, consents and declarations are on chain or in your own files. Nothing to redo.
  • Pass history (the bug-bounty verified tier) lives on a separate observer host that the outage didn't touch. Every window up to 23,580, the last one the old validators scored, is still recorded. Once this release is out, the observer reads the new validators by itself.
  • Points, the leaderboard and the ledger don't depend on the fleet.

The outage rule (testnet rules, Fairness rules, "Void windows"). For scoring and uptime the outage started at window 23,581, the window the fleet was deleted in. The bug bounty's day count keeps the snapshot the validators attested for 23,581 just before, because it holds only tests from before the deletion.

  • The outage itself. Windows 23,581 (the deletion) and 23,582 are void for everyone: the rebuilt validators scored 23,582 with no tester node yet able to reach them.
  • The grace. Windows 23,583 to 23,624 were void for a node that was measured in at least one of the 20 windows before the deletion, until the new validators first measured it. The grace ended at 02:16 UTC on 23 November 2026, 48 hours after tester.4.4 was published. From a node’s first measured window, it counts as usual, and an unmeasured window now counts against uptime as usual.
  • Nobody lost credit for the outage or for upgrading within the grace: a void window never counts against your uptime, an honest-declaration test or the bounty's day count.
  • Nobody gains credit from the gap. Only real measurements earn anything; nothing is filled in for windows nobody measured.

Upgrade your node

Updating takes a single command for most nodes. Every path keeps your keys/ (or /etc/bwos) and your state directory. Don't make new keys and don't bind again. The script is still called migrate-4.4.sh; the one in tester.5.4 reads the version it installs from MANIFEST.json.

First, on every path: download this release into a new directory: the files for your path, plus SHA256SUMS, MANIFEST.json, validator-set.json, network.json, migrate-4.4.sh and bwos-v0.1.0-tester.5.4-linux-<arch> (for bwos doctor). On a kernel node also take install.sh and bwos-validator-v0.1.0-tester.5.4-linux-<arch> (the script reads the chain head with it). Compare sha256sum SHA256SUMS with the hash in the announcement, then check the files and run the commands below from that directory:

sha256sum -c --ignore-missing SHA256SUMS
find . -maxdepth 1 -name '*-linux-*' -exec chmod +x {} +     # downloads come without the executable bit

Below, bwos means this release's ./bwos-v0.1.0-tester.5.4-linux-x86_64 (aarch64 on ARM).

migrate-4.4.sh keeps a copy of everything it replaces, and --dry-run shows what it would do without changing anything. It needs jq. It finds our old public node and the old validators' addresses in the network.json your node kept from its last install (/etc/bwos/network.json, or network.json in the state directory). If that file is gone, add --old-network <the network.json you installed from>; without it, a hand-set peer on our old public node is left as it is, and the script says so.

Kernel node (path A, Ubuntu, root)

sudo bash migrate-4.4.sh kernel

It rewrites /etc/bwos/node.json for the new fleet, keeping the old file as /etc/bwos/node.json.pre-v0.1.0-tester.5.4. It sets the validators' stores (input_peers) and probe agents (probe.peers). If you set cap_sink_allow_from, it swaps the old validators' addresses for the new ones. It sets binding_block to the current block, and replaces our old public node's entry in peers with the new one. Your other peers are left as they are. It checks the new file with install.sh --check-config, then runs install.sh with this release's binaries, validator-set.json and network.json. install.sh builds a current validator set from the chain, checks it against the new validator-set.json ({"event":"anchor_refreshed",...}), installs it and restarts the node.

By hand instead 
OLD=$(jq -r '.transit_peers[0].node // empty' /etc/bwos/network.json 2>/dev/null)   # or the network.json you installed from
BLOCK=$(./bwos-validator-v0.1.0-tester.5.4-linux-x86_64 chain-status --network test --netuid 611 | jq -r '.block // empty')
sudo jq --slurpfile net network.json --arg old "$OLD" --arg block "$BLOCK" '
  .input_peers = $net[0].validator_urls
  | (if has("probe") then .probe.peers = $net[0].probe_peers else . end)
  | (if ($block | test("^[0-9]+$")) then .binding_block = ($block | tonumber) else . end)
  | .peers |= map(if $old != "" and .node == $old
      then ($net[0].transit_peers[0] | {node, uid, binding} + (if (.endpoint // "") != "" then {endpoint} else {} end))
        + (if .listen then {listen: .listen} else {} end) + (if has("bfd") then {bfd: .bfd} else {} end)
      else . end)' /etc/bwos/node.json > node.json
# If you set "cap_sink_allow_from", put the new validators' addresses in it (the hosts in network.json).
bash install.sh --check-config --config node.json        # {"event":"config_ok",...}
sudo bash install.sh --bwos-node ./bwos-node-v0.1.0-tester.5.4-linux-x86_64 --bwos ./bwos-v0.1.0-tester.5.4-linux-x86_64 \
  --bwos-probe ./bwos-probe-v0.1.0-tester.5.4-linux-x86_64 --fabric-sense ./fabric-sense-v0.1.0-tester.5.4-linux-x86_64 \
  --network-json network.json --config node.json --validators validator-set.json

Use the aarch64 files on ARM.

No-root node, in a container (path B)

A restart isn't enough, because the old addresses are on the container's command line. One command recreates it:

sudo bash migrate-4.4.sh container bwos-net-node --sink bwos-cap-sink     # leave out --sink if you run no sink

It copies this release's validator-set.json over the one the container reads from keys/, and puts network.json in state/. It loads bwos-node-v0.1.0-tester.5.4-image.tar, then recreates the container on the new image with the same user, capabilities, read-only root, restart policy, volumes, ports and environment. In the arguments it replaces the store URLs, the --probe-peer entries and our old public node's --peer group (writing its new binding file). In the sink's arguments it swaps the old validators' -allow-from addresses and -validator keys for the new ones, if you used them. Everything else stays. The old container is kept, stopped, until the new one has started; if the new one fails to start, the old one is started again. Bind mounts and named volumes are carried over; any other kind of mount stops the script before it changes anything. It keeps the old container's settings in state/bwos-net-node.pre-migrate.inspect.json. Labels and logging options aren't copied, so if you set any, add them again. A container with tmpfs mounts, security options other than no-new-privileges or an AppArmor profile, sysctls or devices is refused before anything changes: move that one by hand. --memory, --cpus and --pids-limit are carried to the new container. If the script is killed outright midway, sudo bash migrate-4.4.sh restore bwos-net-node puts the old container and files back. The image's System One sees the replaced keys/validator-set.json and starts the node on it.

By hand instead 
docker load -i bwos-node-v0.1.0-tester.5.4-image.tar
sudo cp validator-set.json keys/validator-set.json && sudo chown 65534:65534 keys/validator-set.json
sudo install -m 0644 network.json state/network.json     # root's file, read-only to the node
docker inspect bwos-net-node --format '{{json .Config.Cmd}}' > old-args.json    # your old arguments, to copy from
docker rm -f bwos-net-node
URLS=$(jq -r '.validator_urls | join(",")' network.json)
PROBE=$(jq -r '.probe_peers | map("--probe-peer " + .) | join(" ")' network.json)

Run the same docker run as before (testers.md section 7) on bwos-node:v0.1.0-tester.5.4, with the new $URLS and $PROBE. If your peer was our old public node, use its new card from transit_peers[0]. Keep every other argument and the same keys/ and state/ volumes, and recreate bwos-cap-sink on the new image too.

Check that docker inspect bwos-net-node --format '{{json .Config.Cmd}}' holds no old address.

No-root node, as a process (path B)

How you start the process is up to you, so the script only prints the new arguments:

bash migrate-4.4.sh noroot [--old-network <file>] -- <the arguments you start bwos-node with, after "bwos-node">
bash migrate-4.4.sh sink [--old-network <file>] -- <the arguments you start bwos-probe with, if you run the capacity sink>

Then stop the node (and bwos-probe cap-sink), replace both with this release's binaries, copy validator-set.json over the file you pass to --validators, and start it with the printed arguments (under systemd: edit ExecStart, systemctl daemon-reload, restart). If the script names a binding file, write it as it says. Under System One, also point BWOS_NETWORK_JSON at the new network.json. The node takes the replaced set at its first poll and drops the old one: that's the documented way to leave validators you no longer trust.

Route solver (path D)

Stop the daemon, replace bwos-solver (and your solver) with this release's, and start it with the new --validator-url "$(jq -r '.validator_urls | join(",")' network.json)" and --validator-set validator-set.json. If this release's validator-set.json is more than about a day old when you start, build a current one first (./bwos validator-set build --network test --netuid 611 --fetch "$URLS" --out validator-set.new.json, then mv validator-set.new.json validator-set.json, because --out refuses a file that exists). Nodes build theirs automatically; only a solver does it by hand. Your hotkey and axon stay the same. The daemon keys its held set by the anchor, so it starts afresh from the new one.

Router (Linksys WRT1900AC v1 or GL.iNet GL-MT6000, path C)

In LuCI, Services, Transit Fabric, Setup: choose this release's validator-set.json, press Load the validator set, and enter the new validator_urls as the directory, table and snapshot URLs. To take the new packages without reflashing: opkg install --force-reinstall the three .ipk files. On a GL-MT6000, flash only *-glinet_gl-mt6000-squashfs-sysupgrade.bin: there is no factory image, and OpenWrt warns that one can brick this router. If it already runs OpenWrt 24.10, install the three aarch64_cortex-a53 .ipk files instead. The GL-MT6000 image is built and boot-tested in emulation; it has not been tested on a real router. A router still isn't measured in this release (see Known limitations).

macOS

The Mac build is the bwos CLI only (linking, declarations, doctor on a copied state directory); there is no macOS node in this release. Nothing on the Mac has to change: bwos declare keepalive reads the chain and delivers to your nodes, never to a validator address. Updating it is optional.

Check that it worked

Give it 10 to 15 minutes, then run the check (a failing check in the first minutes is expected: the node takes the new set at its first poll):

sudo bwos doctor --json                                          # kernel node
bwos doctor --json --kind noroot --state-dir state               # no-root process
sudo bwos doctor --json --kind container --state-dir state       # container, from the host

Exit 0, with every check "ok": true, means it worked. To see only what's wrong: ... | jq '.checks[] | select(.ok | not) | {code, fix}'. Also check the probe sessions: jq '.probe_peers[] | {session, stamp_reflected, forwarded_sent}' state/status.json (kernel node: journalctl -u bwos-probe-session -n 50) shows session: true for each of the four agents.

If it didn't work

  • validator_set_retired (new in this release): the node still holds a set signed by the deleted fleet. Its validators file is still the old one. Copy this release's validator-set.json over it again (kernel: re-run install.sh with --validators validator-set.json), and restart.
  • validator_set_pinned: the node couldn't build a current set from the chain at start, so it started on this release's set. That's fine while the set is less than about a day old. Check that the node reaches the chain_endpoints in network.json; System One keeps retrying.
  • validator_set_stale: the set expired before the node reached a validator. Check the validator URLs reach (curl -s <url>/v0/objects/signed-snapshot/latest | head -c 200), and check the node's clock (NTP).
  • No probe session (session: false): an old --probe-peer is left on the command line, or UDP out to the agents' ports is blocked. Compare the command line with probe_peers in network.json.
  • PeerRefused ... binding-expired right after the restart is expected until the first DirectoryApplied (about a minute after the node reaches a validator).
  • Still stuck: open a Bug report at https://github.com/transitfabric/releases/issues with bwos doctor --json and the issue-body.md from bwos report. Your credit is covered by the grace while we sort it out.

What happens if you haven’t upgraded by Sat 2026-11-28 14:51 UTC

At block 8,544,600 validators start naming the peer directory they attest, and at block 8,544,960 scoring version 2 starts. A node on tester.4.4 or earlier can’t read or follow version 2 and isn’t measured by the validators that do. A node on tester.4.3 or earlier also can’t reach the rebuilt fleet at all: bwos doctor shows validator_set_stale, validator_set_rebuild_failed or validator_set_pinned. An unmeasured window counts against uptime as usual, because the outage grace has ended.

Moving the files without the new binaries isn’t enough. Take the binaries too, and for a container, recreate it on the new image.

From an older release (tester.3.x, tester.4 to tester.4.4, or tester.5.x)

The same steps work from any earlier tester release; nothing in between needs installing. migrate-4.4.sh and install.sh take a node from tester.3.x straight to tester.5.4, and a container from tester.3.1 or earlier also loses the owner validator's old forwarder address. A kernel node installed before tester.4 may have no /etc/bwos/network.json: pass --old-network <the network.json you installed from> if you peered with our public node by hand. Before you start, check you still have your node's keys/ (or /etc/bwos); the move keeps them as they are.

A no-root node under systemd

If your no-root node runs as a systemd unit (run-a-node.md section 2a), print its new arguments from its current ExecStart and put them back in the unit:

UNIT=bwos-nr.service                                                   # your unit's name
ARGS=$(systemctl show -p ExecStart --value "$UNIT" | sed -E 's/.*argv\[\]=[^ ]+ (entrypoint )?([^;]*);.*/\2/')
bash migrate-4.4.sh noroot -- $ARGS                                    # the new arguments
sudo systemctl edit --full "$UNIT"     # ExecStart: this release's fabric-sense and BWOS_NODE_BIN, the new arguments
sudo cp validator-set.json <the file your --validators names> && sudo systemctl restart "$UNIT"

The sed keeps what follows fabric-sense entrypoint, or bwos-node for a unit that runs it directly. Point BWOS_NETWORK_JSON in the unit at this release's network.json. The script finds the old network.json in the node's --state-dir by itself.

Peering

Until scoring version 2 starts (block 8,544,960), peering is by hand. Our public node was rebuilt with a new node key and address. It is transit_peers[0] in this release’s network.json, and it is the one to peer with: our kernel reference nodes take only our own fleet’s peers. It reads the open “Peering request” Issues by itself, so your existing request still counts; don’t open a new one. Point your node at the new card (the steps above do it), and our node adds yours once your node is measured by the validators.

From scoring version 2, a node that opted in (see the top of this page) is drawn its peers by the validators each window, and needs no peer card.
